Boot a small Umicom system without changing your computer

Build a diskless Linux guest, follow its first checks and explore a recovery console that does not depend on the desktop.

A practical guide for new developers · C23, Linux, RISC-V and QEMU
Sammy Hegab · Umicom Foundation

1. Meet the small system you will build

Most of the time, an operating system is already running when you open an application. Here you will work one step earlier. You will build the files that let Linux start a small Umicom environment, run two checks and keep a recovery console available.

Your real computer is the host. The small computer created by QEMU is the guest. In this lesson the guest has no attached disk, shared folder or network card. Its files live in memory and disappear when it shuts down. Your source files, compiled output and captured logs stay on the host.

A development exercise, not an installer.

Do not write these files to a USB stick or replace your computer’s operating system. This profile is for direct booting inside QEMU. It does not yet contain Umicom Desk, a graphical login, a general command shell or persistent user storage.

The C components and host-side checks were tested during this source delivery. The Buildroot image and real QEMU boot still need to be built and accepted on your machine. A successful archive check is useful, but it does not mean that Linux has booted. The steps below keep those results separate.

QEMU guest→Linux kernel→Umicom init→Two checks→Ready or recovery

The kernel manages memory, processes and devices. Init is its first user-space process, with process identifier 1. The root filesystem contains paths such as /etc, /dev and /usr. We package that filesystem as an initramfs: a compressed archive that Linux unpacks into memory.

RISC-V is the first target. QEMU’s virt machine supplies the virtual hardware; its packaged OpenSBI supplies the initial firmware. You do not need a physical RISC-V board. A separate x86-64 profile is provided later in the lesson.

2. Put each set of files in the right repository

The source batch has two repository folders. They serve different purposes.

Folder in the batchExample destinationWhat it owns
Umicom-Applications/frameworkC:\umicom\Umicom-Applications\frameworkThe shared report reader and normal user-space Data Server probe.
umicom-osC:\umicom\umicomOSKernel configuration, init, recovery console and image-building recipes.

Close Umicom applications, extract the source batch into a staging folder and compare the supplied files with your checkout. Copy only the included files into matching paths. Do not replace entire folders or delete files that exist only in your checkout. Keep Delivery-Evidence outside both repositories.

The OS repository’s framework submodule is another checkout of the same Framework, not a place to maintain a second implementation. During the first build below we explicitly select the current Framework in Umicom-Applications. The publishing instructions update the OS submodule pin after your Framework commit exists.

Use your own checkout locations where they differ from these examples. The two variables in the next section are the only locations you need to change for the Linux commands.

3. Open the Linux build environment

The existing Windows applications still build with MSYS2 and the normal Umicom preset. Building the Linux guest is a different job: use a Linux machine or WSL. Do not run the following Linux commands in the MSYS2 terminal or ordinary PowerShell.

On Windows, first list your installed WSL distributions:

PowerShell
wsl.exe --list --verbose

Open your existing Debian or Ubuntu distribution from the Start menu. WSL’s initial setup should give you an ordinary Linux account. When no distribution is installed, follow Microsoft’s WSL installation guide; installation can require administrator approval and a restart.

In the Linux terminal, define the checkout locations and a new output directory. /mnt/c is how WSL exposes the Windows C drive. $HOME is your Linux home directory. Build output belongs there, not under the Windows-mounted source tree.

Linux terminal
set -eu
export PATH="/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
OS="/mnt/c/umicom/umicomOS"
FW="/mnt/c/umicom/Umicom-Applications/framework"
BR="$HOME/src/buildroot-umicom"
RUN="$HOME/umicom-builds/riscv64-foundation"

test "$(id -u)" -ne 0 || { echo "Use your normal Linux account, not root."; exit 1; }
test -f "$OS/tools/os_image.py"
test -f "$FW/include/umicom/platform/boot_report.h"
python3 --version
cmake --version

The short PATH applies only to this Linux terminal. It prevents Windows directories containing spaces from being passed into Buildroot. It does not change your Windows environment permanently. set -eu stops a sequence when a command fails or a required variable is missing.

Use Python 3.10 or later and CMake 3.24 or later. The host checks need a C compiler that accepts the C23 or C2x mode selected by CMake. The packaged guest uses Buildroot’s selected GCC 14 toolchain.

4. Install host tools and capture the pinned builder

Buildroot constructs the guest’s compiler, C library and Linux kernel from source. It needs internet access for its first downloads and space in your Linux filesystem for the source and build trees. Check available space with df -h "$HOME". Leave room for a complete compiler and kernel build; the final archive is much smaller than the build tree.

For Debian 13, install the tools below. These commands install software into the Linux host, so they ask for its password. The later build commands must run without sudo.

Linux terminal
sudo apt update
sudo apt install build-essential git cmake ninja-build python3 file cpio     rsync unzip bc bzip2 gzip xz-utils wget curl patch perl     libncurses-dev libssl-dev libelf-dev flex bison     qemu-system-riscv qemu-system-x86 opensbi

Some Ubuntu releases package the RISC-V emulator in qemu-system-misc instead of qemu-system-riscv. Use the package supplied by your distribution, then check the actual executable:

Linux terminal
command -v qemu-system-riscv64
qemu-system-riscv64 --version

Now clone the selected Buildroot release into a new directory. A dependency checkout at a release tag is deliberately detached; it is not a new development branch in an Umicom repository.

Linux terminal
mkdir -p "$HOME/src"
git clone --depth 1 --branch 2025.02.18     https://github.com/buildroot/buildroot.git "$BR"
git -C "$BR" rev-parse HEAD

The commit must be:

Expected Buildroot commit
d030e36bbc9669230c015be971b14b6e062cfdde

An existing clone can be reused only when it is clean and at that exact commit. Do not delete or reset someone’s local changes to make the check pass. The image tool also checks the pin and refuses a dirty Buildroot checkout.

The guest selects Linux 6.12.109. Its source-archive hash is recorded in image/versions.json and in the selected Buildroot release’s kernel hash list. These pins make inputs identifiable; they do not replace future maintenance or prove that every component is free of defects.

5. Test the C components before building a kernel

These checks run as normal programs on your Linux host. They test configuration parsing, real child-process supervision, console input and report compatibility. They do not start guest init as PID 1 or mount filesystems.

Linux terminal
cmake -S "$OS/boot/foundation"     -B "$HOME/umicom-checks/os-foundation" -G Ninja     -DCMAKE_BUILD_TYPE=Release     -DUMICOM_OS_FRAMEWORK_SOURCE="$FW"
cmake --build "$HOME/umicom-checks/os-foundation" --parallel 2
ctest --test-dir "$HOME/umicom-checks/os-foundation"     --parallel 2 --no-tests=error --output-on-failure

A separate privilege-switch test can be skipped under an ordinary account, inside a restricted container or in a sanitiser build. A skip is not a pass for that capability. The real boot test must still prove that guest services run under the intended identity.

Next, build the normal Framework probe and run its memory-only self-test:

Linux terminal
cmake -S "$FW/examples/os_foundation"     -B "$HOME/umicom-checks/framework-probe" -G Ninja     -DCMAKE_BUILD_TYPE=Release
cmake --build "$HOME/umicom-checks/framework-probe" --parallel 2
ctest --test-dir "$HOME/umicom-checks/framework-probe"     --no-tests=error --output-on-failure

The probe checks that an uncommitted Data Server update can be rolled back and a committed update can be read. It explicitly says that no guest boot was attempted. Do not run umicom-os-init directly: it refuses to run unless it is the guest’s privileged PID 1.

6. Freeze the inputs, then build

Preparing an image makes a small snapshot of the source files selected by the profile. This is different from copying an entire repository. An existing Linux source checkout under kernel, personal files and unrelated applications are not swept into the snapshot.

Linux terminal
python3 "$OS/tools/os_image.py" prepare     --buildroot "$BR" --framework "$FW"     --output "$RUN" --arch riscv64

You should see a message saying that inputs were captured and that no image has been built or booted. Inspect $RUN/input-manifest.json. It records the architecture, selected versions and hashes of the captured source files. Git revisions and dirty state are recorded when available.

An uncommitted source merge is normal during development. Its manifest must not pretend to be a clean release. For a release candidate, finish your commits and create a fresh image output directory from the published source.

Start the build:

Linux terminal
python3 "$OS/tools/os_image.py" build --output "$RUN" --jobs 2

This is the long step. Buildroot downloads the selected sources, builds a cross-compiler and compiles the guest. --jobs 2 limits the package build parallelism. It does not mean there are two guest processors.

Keep the terminal output when a build fails. Correct a host dependency first, then rerun build against the same captured input. When changing an Umicom source file or profile, make a new RUN directory and prepare again. Do not edit files inside the frozen snapshot to hide a mismatch.

7. Assemble and inspect the root filesystem

Compiling files is not the same as assembling a boot image. The pack step selects only the three guest programs, their configuration and a small set of directories and device entries. It does not turn the entire Buildroot staging tree into the guest.

Linux terminal
python3 "$OS/tools/os_image.py" pack --output "$RUN"
python3 "$OS/tools/os_image.py" verify --bundle "$RUN/bundle"

The new bundle directory contains:

FilePurpose
ImageThe RISC-V Linux kernel. The x86-64 profile uses bzImage.
umicom-rootfs.cpio.gzThe compressed RAM-root archive.
source-manifest.jsonThe input identity that the guest reports.
image-manifest.jsonFile hashes, rootfs inventory and the explicit status not-run.

Verification checks the headers, static program architecture, archive paths, modes, sizes and hashes. A changed file or unexpected entry is rejected. Neither this inventory nor its checksum is a digital signature.

There is still no boot result. The message deliberately says that integrity verification does not prove the image boots. Repacking also refuses an existing destination; preserve it and choose a new --bundle directory when making another candidate.

8. Run the normal boot check

This is where a real QEMU process starts the virtual computer. The runner attaches the kernel and initramfs directly, uses one software-emulated processor and captures the serial console. It does not attach a host disk, network card or shared folder.

Linux terminal
python3 "$OS/tools/os_image.py" boot --bundle "$RUN/bundle"     --mode normal --log "$RUN/normal-boot.log"

Use a new log filename for each attempt. The runner saves the serial text and a separate JSON result. It will not reuse an old transcript as a successful run.

A successful default boot is expected to show the following sequence. This is an expected sequence, not a claim that this image was booted in the delivery environment:

Expected serial output
UMICOM_INIT pid=1
UMICOM_SERVICE start=platform-check
UMICOM_SERVICE end=platform-check outcome=none exit=0 signal=0
UMICOM_SERVICE start=framework-probe
UMICOM_SERVICE end=framework-probe outcome=none exit=0 signal=0
UMICOM_REPORT_BEGIN
UMICOM_BOOT_REPORT 1
mode=normal
state=ready
planned=2
completed=2
reason=none
source=<the actual 64-character source fingerprint>
UMICOM_REPORT_END
UMICOM_SHUTDOWN

The runner requires the guest report, matching source identity, expected service order and a clean QEMU exit. A kernel panic, timeout or unsuccessful run is recorded as a failure. Missing QEMU produces NOT RUN and exit code 77, not a success.

Ready has a narrow meaning: both one-shot checks completed during this boot. It does not mean that a desktop is installed or that every Umicom application is operational.

9. Prove that recovery does not start normal services

A useful recovery route must not depend on the part of the system you are trying to diagnose. Here the recovery controller is a separate, small C program. It does not link Framework, GTK or a database library.

Run the same image with a different boot request:

Linux terminal
python3 "$OS/tools/os_image.py" boot --bundle "$RUN/bundle"     --mode recovery --log "$RUN/recovery-boot.log"

The expected final report has mode=recovery, state=recovery, completed=0 and reason=requested. There must be no normal service-start messages. A successful recovery run proves a different property from a successful normal run; keep both results.

To inspect the console yourself, start an interactive run:

Linux terminal
python3 "$OS/tools/os_image.py" boot --bundle "$RUN/bundle"     --mode recovery --interactive

Type one command at a time:

Inside the guest console
help
status
packages
log platform-check
poweroff

In forced recovery there may be no platform-check log because that service was never started. That absence is expected. A normal interactive boot lets you read both service logs. The console accepts a known service identifier, not a path such as ../etc/shadow. Long commands and unsupported control characters are rejected.

poweroff requests shutdown of the guest. reboot requests its reboot; the supplied QEMU command uses -no-reboot, so QEMU exits rather than entering a restart loop. Neither command reboots the Windows or Linux host.

10. Read the configuration and make one careful change

Open rootfs/foundation/etc/umicom/boot.conf in your editor. Each service line names the check, the single packaged executable, its predecessor and its deadline in milliseconds:

Boot configuration
UMICOM_OS_BOOT 1
hostname=umicom
service=platform-check|/usr/libexec/umicom-platform-check|-|3000
service=framework-probe|/usr/libexec/umicom-framework-probe|platform-check|5000

A dash means that the first service has no predecessor. The second service cannot run until platform-check succeeds. The parser checks the complete graph before launching anything: duplicate identifiers, missing dependencies, cycles and invalid paths stop the normal route.

For a first exercise, change only the hostname to umicom-practice, prepare a new output directory and build another candidate. Compare the two source fingerprints. Do not change the two service names while using the default smoke test: that test deliberately expects this starter sequence.

For the x86-64 variant, repeat preparation with a new output directory and --arch x86_64, then run the same build, pack, verify and two boot commands. Changing a filename from Image to bzImage is not a conversion between architectures.

Check your understanding

Why can archive verification succeed before any guest has run? Why should forced recovery have zero completed services? Which files disappear when the guest shuts down, and which logs remain on the host? Find the answers in your actual manifests and transcripts rather than relying only on the word “passed”.

11. When a step stops

Message or symptomWhat to do next
Existing output directoryKeep it. Choose a new output or log name; do not overwrite evidence from a previous attempt.
Buildroot pin or dirty-tree rejectionInspect the dependency checkout. Use a clean clone of the recorded commit rather than resetting unrelated work.
Frozen input changedCreate a new prepared snapshot. Editing the manifest to match an unexplained change defeats its purpose.
Missing host packageInstall the named development dependency in Linux, then retry the same build. Do not bypass source hash checks.
NOT RUN: QEMU unavailableInstall the correct system emulator and check its executable and firmware. No boot result exists yet.
Timeout, panic or service failureRead the serial log and JSON result. Try forced recovery. Do not treat a host unit-test pass as a substitute.
Unexpected ELF or kernel headerCheck the architecture and static-link settings. Do not rename a wrong binary or weaken the check to continue.

Run the boot command from a maintained Linux/WSL environment using trusted source and image files. Not attaching a disk or network card reduces the guest’s reach, but it is not a promise that an emulator can run hostile machine code without risk.

12. Keep a useful record of the result

Before publishing a candidate, retain its input manifest, image manifest, source revisions, QEMU version and both boot transcripts. A software update is easier to investigate when someone else can identify the exact inputs and see which checks actually ran.

Linux terminal
python3 "$OS/tools/os_image.py" legal-info --output "$RUN"

Inspect the generated licence and source records and every warning before distributing built binaries. The Umicom MIT notices do not change the licences of Linux, the C library, Buildroot or firmware. This source batch does not include those third-party binaries.

Commit the shared Framework work first, then update and commit the OS repository’s Framework pin. Commit the Applications parent lock last. The accompanying Build-and-Git.md contains the full PowerShell sequence, including the normal Windows build and regression tests.

The next stage is normal desktop user-space: a persistent storage policy, supervised services and Umicom Desk. Keep this small recovery layer independent as those features grow.
